# Environment setup

## Prerequisites

Node ≥ 22, pnpm 12 (`corepack enable` or `npm i -g pnpm`), and [uv](https://docs.astral.sh/uv/), which installs Python 3.12 itself. FFmpeg/ffprobe must be on PATH for upload validation. Docker is **optional** (ADR-0002).

```bash
pnpm install                 # JS deps (workspace)
uv sync --all-packages       # Python deps (api, worker, contracts) into .venv
pnpm env:init                # creates .env from .env.example and generates the two machine secrets
pnpm dev                     # web on :5173 (proxies /api) + API on :8000
pnpm worker                  # second terminal: runs jobs (test pipeline + standard pipeline)
# then open http://127.0.0.1:5173 and create the operator account (first run only)
```

## Secret handling rules

- `.env` is git-ignored. Only the blank template `.env.example` is committed. Never paste secret values into chat, issues, screenshots or logs.
- The API reads secrets as `SecretStr`. `/api/ready` reports only **present / blank**, never values.
- College SyncVDI login credentials are **not** product configuration. They never go in `.env`, code, tests or URLs. You sign in to the portal yourself.
- `pnpm env:init` fills only **blank** `NAZAR_SECRET_KEY` / `NAZAR_WORKER_TOKEN` with random values and prints only the variable names. It never overwrites a value you set and never touches API-key placeholders.
- To generate a secret by hand: `uv run python -c "import secrets; print(secrets.token_urlsafe(48))"`

## Variables

### Required: generated by you, no third-party account needed

| Variable | Purpose |
|---|---|
| `NAZAR_SECRET_KEY` | Signs short-lived artifact download links and session cookies. Random ≥ 48 chars. |
| `NAZAR_WORKER_TOKEN` | Bearer token the GPU worker uses to lease jobs / upload artifacts. Random ≥ 48 chars; set the same value on the worker host. |
Both are generated by `pnpm env:init`. While either is blank the API still runs, `/api/ready` reports `ready: false`, and the web UI shows "API online · not ready".

### Operator account

On first run the web app shows **Create the operator account**. That endpoint works only while no account exists, only from a loopback client, and never when `NAZAR_ENV=production`. The password is hashed with scrypt. Sessions are HttpOnly, SameSite=Lax cookies (Secure in production), and only a SHA-256 of the session token is stored. `/api/ready` reports `accounts` as not configured until an account exists.

Headless/production alternative: set `NAZAR_BOOTSTRAP_ADMIN_EMAIL` and `NAZAR_BOOTSTRAP_ADMIN_PASSWORD`; the account is created on start if none exists. Both are optional.

### Optional

| Variable | When to set |
|---|---|
| `NAZAR_DATABASE_URL` | Use PostgreSQL/PostGIS instead of the SQLite default, e.g. `postgresql+psycopg://nazar:<pw>@127.0.0.1:5432/nazar`. |
| `NAZAR_REDIS_URL` | Only for multiple API instances. |
| `NAZAR_S3_ENDPOINT_URL`, `NAZAR_S3_BUCKET`, `NAZAR_S3_ACCESS_KEY_ID`, `NAZAR_S3_SECRET_ACCESS_KEY` | S3-compatible (MinIO) artifact storage instead of local disk. |
| `HF_TOKEN` | Hugging Face token. Needed only if a chosen model's weights are gated, or to avoid anonymous rate limits on the GPU host. Create at huggingface.co → Settings → Access Tokens (read scope). |

### Not needed for local development

`POSTGRES_PASSWORD`, `MINIO_ROOT_USER` and `MINIO_ROOT_PASSWORD` are used only by `infra/docker-compose.yml`.

### Non-secret settings (defaults in `.env.example`)

| Setting | Meaning |
|---|---|
| `NAZAR_ENV` | Runtime environment (default `development`). |
| `NAZAR_LOG_LEVEL` | Log level (default `INFO`). |
| `NAZAR_API_HOST`, `NAZAR_API_PORT` | Where the API listens (`127.0.0.1:8000`). |
| `NAZAR_WEB_ORIGINS` | Browser origins allowed by CORS. |
| `NAZAR_STORAGE_DIR` | Root for uploads, artifacts and the SQLite file (`var/storage`, git-ignored). |
| `NAZAR_MAX_UPLOAD_MB`, `NAZAR_MAX_VIDEO_SECONDS` | Upload and duration limits. |
| `NAZAR_GPU_MAX_CONCURRENT_JOBS` | Heavy GPU jobs per worker. Keep at 1. |
| `NAZAR_API_BASE_URL` | Where the worker finds the API. |
| `NAZAR_PIPELINE_MODE` | `test` = deterministic fixture pipeline; `real` = research models. |

## GPU models (optional; the full standard pipeline)

Without them, Reconstruct uses the CPU baseline (classical structure-from-motion) and says so in the job. With them, the standard pipeline runs every model in sequence, each contributing to the final 3D model (see `docs/pipeline-completion/06-FULL-PIPELINE-PLAN.md`):

| Stage | Model | Contributes |
|---|---|---|
| dynamic_analysis | YOLO11 (Ultralytics, AGPL-3.0) + SAM 2.1 (Apache-2.0) | masks of objects that moved, kept out of poses, cloud, mesh and splat |
| geometry | Fast3R ViT-L/512 (FAIR Noncommercial) | camera poses + dense pointmaps |
| depth_priors | Metric3D-v2 (BSD-2-Clause) | metric depth + normals: scale evidence, mesh normals, hole fill |
| dense_reconstruction | fusion + gsplat (Apache-2.0) | fused cloud; photoreal Gaussian splat (InstantSplat-style, poses refined) |
| surface_processing | Open3D screened Poisson (MIT) | coloured triangle mesh with per-vertex confidence |

Licences: Fast3R is approved for this academic, non-commercial project only; Ultralytics' AGPL-3.0 was accepted for the same project. Neither approval extends to commercial use.

The worker never imports torch. Each model runs as a subprocess of one of two pinned environments under `var/gpu/` (git-ignored; ADR-0004):

| Environment | Python / torch | Holds | Pins |
|---|---|---|---|
| `var/gpu/main-env` | 3.11 / 2.6.0+cu124 | Fast3R, Open3D, YOLO, SAM 2, Metric3D-v2 | `apps/worker/gpu/requirements-main.txt` |
| `var/gpu/splat-env` | 3.10 / 2.4.1+cu124 | gsplat 1.5.3 (prebuilt CUDA wheel exists only for this combination) | `apps/worker/gpu/requirements-splat.txt` |

Model sources are pinned to commits (`fast3r-src`, `sam2-src`, `metric3d-src`), weights to revisions and SHA-256 where published. `scripts/setup_gpu.py` installs and checks everything; it lists what is missing with approximate sizes and asks before downloading:

```bash
pnpm gpu:check                                     # read-only: sources, envs (CUDA), weights
pnpm gpu:setup                                     # local profile (~7.5 GB first time)
uv run python scripts/setup_gpu.py --profile clg   # college GPU weights (adds ~6.5 GB)
```

No `.env` change is needed: the worker finds `var/gpu` by itself. `NAZAR_GPU_PYTHON`, `NAZAR_SPLAT_PYTHON`, `NAZAR_GPU_WEIGHTS` (and the older `NAZAR_FAST3R_*`) override the locations; setting one to an empty value disables it.

### Two compute profiles

| | `local` (laptop, 6 GB) | `clg` (college VDI, 30+ GB) |
|---|---|---|
| GPU memory | each model process capped at 5,632 MiB (allocator + CUDA context); peak measured and reported | no cap |
| Models | YOLO11s, SAM 2.1 small, Metric3D ViT-Large (ViT-Small if Large does not fit), Fast3R in passes sized to the budget, splat 4k iterations / 400k Gaussians, SH degree 1 | YOLO11x, SAM 2.1 large, Metric3D ViT-giant2, Fast3R up to 48 views per pass, splat 15k iterations / 2M Gaussians, SH degree 3 |
| If a model does not fit | skipped with a visible reason (only here) | the job fails: every model must run |

The worker's `--location` picks the profile (`local` or `college`). To run the whole pipeline on one video without the API or web app:

```bash
uv run --package nazar-worker python scripts/test_full_pipeline.py --video docs/sample/video/sample1.mp4 --how local
```

It prints every stage as it runs, then a summary: what each model contributed, peak GPU memory per model against the budget, and the artifacts (point cloud, LAS, GLB, mesh GLB, splat PLY, masks, depth previews, report) under `var/runs/<video>-<how>/`.

**Windows memory note.** On Windows (WDDM), GPU allocations are also charged to the system *commit* limit (RAM + page file), so the runner needs about 2.3 GiB plus its peak VRAM of free commit (≈ 5–8 GiB). When commit runs out, CUDA fails with `unknown error` or `Memory allocation failure` and the job falls back to the CPU baseline with that reason. If that happens, close memory-heavy apps or let Windows grow the page file. Linux hosts (the college VDI) do not charge commit this way.

## College GPU (SyncVDI) workflow, as far as it is known

1. You sign in at the SyncVDI portal and request a session. Platform **Linux** is preferred for CUDA research code; pick the GPU, RAM and duration there.
2. When the session is **Ready**, Connect downloads an RDP/VNC file. Open it with your remote-desktop client.
3. Inside the session, clone the repo and run the read-only diagnostics: `uv run --package nazar-worker nazar-worker doctor`. This is Milestone 1. It reports GPU, VRAM, disk and toolchain, and installs nothing.
4. Still to be confirmed, with read-only checks or college support:
   - whether outbound HTTPS from the VDI can reach the API (ADR-0003);
   - persistent storage location and quota;
   - whether `pip`/`uv` downloads and Hugging Face downloads are allowed (needed once, for `pnpm gpu:setup`; it can also be pointed at weights copied in by hand via `NAZAR_FAST3R_WEIGHTS`);
   - session maximum duration.

Never leave the only copy of results in the VDI session. Do not run heavy GPU jobs speculatively on shared hardware.
